## 結論

兩份指定舊腳本的 **96 次＋30 次案例均符合預期，舊誤報已修正**。但新增邊界測試發現：

1. ［P2］被拒絕或未關閉的字串會重新同步到內部／結尾引號，刪掉本應保留的公式，不符合「失敗時寧可攔下」。
2. ［P2］同引號巢狀 f-string 被提前結束，可能誤報合法內容，也可能吞掉外部公式。
3. ［P3］反引號掃描只檢查第一次找到的候選，遇到內部較長的反引號 run 就放棄，會誤報合法的程式碼片段。

這些是新增的驗證器反例，並非目前 835 題已存在的題目錯誤，也不是執行程式／資料安全漏洞；風險是內容檢查放過未渲染公式或擋住正常程式範例。

## 1. 拒絕／未閉合字串後的恢復掃描會吞公式

位置：`src/content/codeLiterals.ts` 的 `stripCodeLiterals()`。候選字串因邊界不合法或未閉合而失敗後，只前進一字元，後續引號仍可能被當成新的開頭。

### 1a. 中文／識別字後的開頭被拒絕，結尾卻重新當成開頭

```text
中文"abc "；$x^2=4$；"end"
bar"x " + $x^2=4$ + "y"
if"x " + $x^2=4$ + "y"
```

第一個引號前面接中文字或識別字，因 `isIdent()` 被拒絕；但原結尾引號前是空格，符合開頭條件，因此從那裡一路移除至下一段引號，連外面的 `$x^2=4$` 一起刪除。實測三個欄位均回報 **0 個 LaTeX 錯誤**。

例如第二行的掃描結果為 `bar"x  y"`，公式已消失。`foobar`、`foo_f` 及中文後直接接 r 前綴也重現；合法 b 前綴加外部公式的控制案例正常攔截。

`bar"…"` 這種組合不是合法 Python 表達式，正因無法辨認，依本次要求應保留可疑文字供後續攔截，而非重新解讀結尾引號並吞掉外部公式。中文案例則是一般題目敘述可能出現的引述格式。

### 1b. 未關閉三引號的內容被重新當成普通字串

```text
r"""first line
"$x^2=4$"
```

沒有任何結束三引號。初次掃描失敗後，掃描器仍繼續處理後面的引號，最後輸出 `r" first line\n `，公式被刪除，三欄位皆為 0 個 LaTeX 錯誤。

對照：單純未關閉三引號且後面沒有引號組合的案例，公式仍會被攔截。問題在錯誤狀態下再次辨認內部引號，不能由簡單未關閉案例通過就宣稱保守失敗成立。

建議：明確定義「候選遭拒／未閉合」的恢復規則，避免將其結尾或內部引號重新用來開啟豁免範圍。對無法可靠界定的區域保留原文；對未閉合三引號，至少不要再刪除其後內容中的公式。新增斷言應確認外部公式仍在輸出中，而不只是函式不拋錯。

## 2. 同引號巢狀 f-string 會被提前截斷

位置：`src/content/codeLiterals.ts` 的 `scanPythonString()`。目前只尋找下一個未跳脫的外層引號，不辨識 f-string 替換欄位的括號／內部字串。

### 合法程式被誤報

```python
rf"{data["key"]} \(ok\)"
```

已用本機 CPython 3.14.10 的 `ast.parse()` 及實際 `eval()` 驗證，`data={'key':'value'}` 時得到 `value \(ok\)`，沒有語法警告。這類同引號重用是該版本支援的語法。

掃描器卻在 `key` 前的雙引號就停止，剩下 ` key"]} \(ok\)"`，導致題幹／選項／解析均誤報 1 次。

### 同一缺口也會吞掉字串外公式

```text
f"{data["key"]}"；$x^2=4$；"end"
```

外部公式本來應攔下，實際卻輸出 ` key"]} end"`，三個欄位均為 0 個錯誤。這不是刻意把公式包進程式字串的既知豁免：公式原本在 f-string 之外。

對照：使用不同內外引號的 `f"{data['key']} …"`、所測大括號／字典案例及沒有後續字串的外部公式案例可通過。這些正向案例不涵蓋同引號重用與後續重新同步。

建議：支援 f-string 替換欄位的必要狀態，或在不支援時明確保留原文而不移除半截；不必宣稱完整 Python parser，但必須避免把錯誤邊界延伸到外部公式。

證據：`docs/audit-2cfd9e4-fstring.log`、本輪 probes 的 `f-nested-same-quotes` 與 `f-nested-outside-following-string`。

## 3. 反引號 run 的搜尋只看第一個候選

位置：`src/content/codeLiterals.ts` 中 `text.indexOf(fence, i + n)` 與其後的 run 長度判斷。

測試文字（外層各一個反引號，內部有兩個）：

```text
`\(a\)``inner`
```

開頭與最後的反引號數量相同，內部的較長 run 應跳過，再繼續尋找長度相等的結尾。以現有 remark 解析，確實得到一個 inlineCode：`\(a\)``inner`。

掃描器第一次遇到內部兩個反引號就放棄，沒有繼續找最後的一個，因而原文留下，三個欄位皆誤報 LaTeX。

建議：按完整連續 run 長度掃描，跳過長度不同的候選，再找後面的相等 run；找不到時才保留原文。單純不成對的反引號控制案例仍應維持保守，不吞公式。
